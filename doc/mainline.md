# Milestone 项目主线设计文档

> 文档状态：基线版本 1.0
>
> 适用范围：产品设计、RN 开发、Solidity 开发、Node.js 服务、AI 测试、代码审查和后续迭代。
>
> 本文是本项目的最高优先级产品约束。后续设计、开发、测试和 CR 都必须以本文为准。旧的个人学习工具、课程管理工具或“21 天学习计划”方案不再作为本项目的产品主线。

---

## 1. 项目定义

### 1.1 产品暂定名称

**Milestone（里程碑）**

名称可以在产品验证后调整。名称不是当前开发重点，当前重点是验证业务闭环和技术可行性。

### 1.2 一句话定义

Milestone 是一个面向独立开发者、设计师和小型工作室的链上项目托管与里程碑分账 App。

它让项目合作双方把项目拆成若干个里程碑，把付款放入智能合约托管，乙方提交交付证据，甲方确认后按规则释放对应款项，并保留可验证的项目记录。

### 1.3 核心价值

产品必须同时为合作双方提供价值：

- 甲方：减少先付款后无法交付的风险，清楚看到项目进度和交付证据。
- 乙方：减少交付后收不到款的风险，按已确认的里程碑获得付款。
- 团队：明确多人分工和分账规则，减少人工统计和重复沟通。
- 平台：通过标准化的项目、里程碑、提交和付款记录，提供可信的合作基础设施。

### 1.4 最小业务闭环

```text
创建项目
  -> 约定参与方、金额、里程碑和验收规则
  -> 甲方将测试代币或可支持的资产存入托管合约
  -> 乙方提交交付证据
  -> 甲方确认里程碑
  -> 合约释放当前里程碑资金
  -> 记录链上交易和链下交付资料
```

MVP 只需要把这一条闭环做稳定。没有完成闭环之前，不增加市场、社交、积分、代币或复杂治理功能。

## 2. 为什么要使用区块链

### 2.1 区块链必须解决真实问题

区块链在本项目中只承担四类职责：

1. **资金托管**：平台后端不能单方面把托管资金转走。
2. **规则执行**：里程碑确认、超时释放和分账规则由合约执行。
3. **共同证据**：关键状态和交易结果可以由任何参与方验证。
4. **可移植记录**：合作完成记录和交易凭证不完全依赖平台数据库。

如果某项功能只涉及页面展示、搜索、通知或 AI，总体上应该放在链下，不要为了“Web3”强行上链。

### 2.2 不做的 Web3 方向

本项目不以以下内容作为产品主线：

- 不发行平台代币。
- 不做 NFT 展示或空投工具。
- 不做 DAO 治理平台。
- 不做纯钱包管理器。
- 不做交易所或投资产品。
- 不用连续签到、积分和抽奖制造虚假活跃。
- 不把用户的隐私资料、合同全文和文件原文直接写入公链。

### 2.3 合规边界

第一阶段只在测试网使用模拟代币，验证合约和应用流程，不处理真实资金。

如果未来进入生产环境，必须在目标地区重新评估：

- 托管和转账是否需要许可或合作方。
- 稳定币支付是否受到地区限制。
- 用户身份和反洗钱要求。
- 争议处理和合同责任归属。
- 隐私、数据删除和跨境数据传输。

在未完成合规评估、合约安全审计和运营责任确认前，不对外宣称真实资金托管服务。

## 3. 目标用户与业务场景

### 3.1 第一目标用户

第一目标用户不是所有 Web3 用户，而是以下较窄的人群：

- 独立软件开发者。
- 独立设计师和产品顾问。
- 2—10 人的小型软件或设计工作室。
- 有固定外包项目的技术团队。
- 需要分阶段付款的跨地域项目合作双方。

### 3.2 典型角色

| 角色 | 主要任务 | 核心诉求 |
| --- | --- | --- |
| Client 甲方 | 创建项目、存入资金、确认交付 | 交付可追踪，资金按结果付款 |
| Contractor 乙方 | 接受项目、提交成果、申请释放资金 | 按节点获得明确付款 |
| Contributor 成员 | 完成具体工作、提交证据 | 任务和分账清楚 |
| Admin / Arbitrator 仲裁者 | 在争议时查看证据并执行规则 | 权限有限、过程可追踪 |

MVP 先支持甲方和乙方两种角色。多人 Contributor 和独立仲裁者作为后续阶段，不提前做复杂权限体系。

### 3.3 典型项目示例

例如甲方委托开发一个小程序：

- 里程碑 1：完成产品原型，付款 20%。
- 里程碑 2：完成登录、首页和核心业务，付款 40%。
- 里程碑 3：完成测试包和部署，付款 40%。

乙方每完成一个节点，提交 GitHub PR、测试包地址、截图和说明。甲方查看后确认，合约释放该节点的金额。

产品第一阶段只要适用于这类项目即可，不需要覆盖所有行业合同。

### 3.4 不服务的用户

- 需要高频交易或投资建议的人。
- 需要匿名洗钱或规避监管的人。
- 需要复杂企业采购、发票和财务系统的人。
- 只想使用待办事项而没有项目付款场景的人。
- 需要平台代替自己判断交付质量的人。

## 4. 产品原则

### 4.1 可信优先

与资金、角色、里程碑状态和释放结果有关的关键数据，最终以链上状态为准。数据库可以缓存和索引，但不能伪造链上结果。

### 4.2 可用优先

用户不需要理解区块链内部细节才能完成一次项目操作。App 必须用清楚的语言解释：当前状态、需要谁操作、会产生什么交易、交易是否成功。

### 4.3 最小范围

每一阶段只实现一个可验证的业务闭环。新功能必须说明：

- 解决了哪个已确认的问题；
- 属于哪个产品阶段；
- 是否改变合约和数据模型；
- 是否增加安全、合规和运维成本。

### 4.4 不依赖 AI 才能工作

AI 只能帮助用户理解和整理信息，不能替代资金释放、权限验证和最终确认。AI 失败时，用户仍然可以手动完成核心流程。

### 4.5 先测试网，再考虑真实资金

开发、演示和测试阶段使用 EVM 测试网和模拟代币。任何真实资产能力都必须单独评估，不得因为 Demo 成功就默认可以生产部署。

## 5. 产品范围分阶段确定

### 5.1 P0：必须完成的 MVP

目标是让两个测试用户完成一个完整项目闭环。

#### 钱包和身份

- 连接外部 EVM 钱包。
- 显示当前网络和钱包地址。
- 支持断开钱包。
- 钱包地址作为链上身份，不在服务端保存私钥。
- 服务端可以保存钱包地址、显示名称和应用偏好。

#### 项目

- 创建项目。
- 设置项目名称、描述、甲方、乙方和币种。
- 设置项目总额和截止时间。
- 编辑尚未托管资金的项目。
- 查看项目基本状态和交易记录。

#### 里程碑

- 创建 1—5 个里程碑。
- 设置标题、描述、金额、截止时间和验收说明。
- 显示每个里程碑的状态和付款金额。
- 按固定顺序完成里程碑。
- MVP 中不支持任意复杂的依赖关系和任务树。

#### 托管和释放

- 甲方批准项目的托管金额。
- 甲方将模拟代币存入 Escrow 合约。
- 乙方提交里程碑交付说明和证据链接。
- 甲方确认里程碑。
- 合约释放该里程碑金额给乙方。
- App 展示交易等待、成功和失败状态。

#### 交付证据

- 支持 URL、文本说明和图片链接。
- 图片和文件放在对象存储或本地开发存储，链上只记录哈希或引用标识。
- 证据创建后保留版本记录，不直接覆盖旧内容。
- MVP 不做文件协同编辑和在线预览编辑器。

#### 基础通知

- 里程碑提交后提醒甲方。
- 甲方确认后提醒乙方。
- 交易失败或长时间未确认时提醒相关用户。
- 通知可以先使用站内消息，移动推送放在 P1。

### 5.2 P1：验证真实使用后的功能

只有 P0 被真实用户使用并发现明确需求后，才进入 P1：

- 里程碑超时释放规则。
- 简单争议状态和指定仲裁者。
- 多人分账。
- GitHub 仓库和 PR 关联。
- 邮件和移动推送。
- AI 项目条款摘要和交付说明检查。
- 公开的项目完成凭证。
- 项目模板。
- 基础数据统计。

### 5.3 P2：暂不承诺

- 多链支持。
- 跨链桥接。
- 真实稳定币支付。
- 平台撮合市场。
- 复杂仲裁网络。
- 信誉评分体系。
- 保险和融资。
- 平台代币。
- DAO 治理。

这些内容可能有价值，但会显著增加合约风险、合规成本和运营复杂度，不属于当前主线。

## 6. 核心用户流程

### 6.1 创建项目

1. 甲方连接钱包。
2. 选择“创建项目”。
3. 填写项目名称和简短描述。
4. 填写乙方钱包地址或邀请链接。
5. 创建里程碑并填写金额、截止时间和验收说明。
6. 查看总金额和里程碑金额是否相等。
7. 提交项目草稿。
8. 甲方确认托管，钱包弹出交易签名。
9. App 等待链上确认。
10. 合约确认成功后，项目进入“进行中”。

### 6.2 乙方接受项目

1. 乙方连接钱包。
2. 打开邀请链接或项目详情。
3. 检查甲方地址、项目金额、里程碑和截止时间。
4. 接受项目。
5. 如果发现内容不正确，拒绝接受并返回修改原因。

MVP 可以先由甲方直接填写乙方地址，接受动作只作为页面状态，不做复杂的签名合同流程。

### 6.3 提交里程碑

1. 乙方进入当前里程碑。
2. 添加交付描述。
3. 添加至少一个证据链接或文本说明。
4. 提交交付。
5. App 保存链下提交记录。
6. 必要时写入提交哈希或链上提交状态。
7. 甲方收到待确认提醒。

### 6.4 确认并释放资金

1. 甲方查看里程碑说明和证据。
2. 甲方选择“确认并释放”。
3. App 清楚展示金额、接收地址、网络和手续费提示。
4. 甲方在钱包中签名。
5. App 显示交易等待状态。
6. 链上事件确认后，里程碑状态变为已释放。
7. 乙方看到收款交易链接。

### 6.5 失败和重试

所有链上操作都必须支持以下状态：

- 尚未发起；
- 钱包等待签名；
- 已提交交易；
- 等待区块确认；
- 已成功；
- 已失败；
- 可重试。

App 不得因为 API 返回成功就直接显示资金已释放，必须等待链上确认或通过事件索引确认。

### 6.6 MVP 的异常处理

| 异常 | 用户看到的结果 | 处理方式 |
| --- | --- | --- |
| 用户拒绝签名 | 操作未完成 | 保留当前页面，可重新发起 |
| RPC 暂时不可用 | 状态未知 | 显示查询中，后台重试 |
| 交易失败 | 未改变链上状态 | 展示失败原因和重试按钮 |
| 重复点击确认 | 不能重复释放 | 合约状态校验和按钮锁定 |
| 数据库暂时不可用 | 不能同步页面 | 显示重试，不伪造成功状态 |
| 证据链接失效 | 仍保留提交记录 | 显示链接不可访问，不删除链上记录 |

## 7. 状态机

### 7.1 项目状态

```text
draft
  -> awaiting_funding
  -> active
  -> completed

draft -> cancelled
awaiting_funding -> cancelled
active -> paused
paused -> active
active -> disputed       # P1
disputed -> active       # P1，争议解决后
disputed -> completed    # P1
```

MVP 只实现：`draft`、`awaiting_funding`、`active`、`completed`、`cancelled`。

### 7.2 里程碑状态

```text
pending
  -> available
  -> submitted
  -> approved
  -> released

available -> postponed
submitted -> revision_requested
revision_requested -> submitted
submitted -> disputed       # P1
```

MVP 只实现：`pending`、`available`、`submitted`、`released`、`cancelled`。

### 7.3 资金状态

```text
not_funded
  -> funding_pending
  -> funded
  -> release_pending
  -> released

funding_pending -> funding_failed
release_pending -> release_failed
```

链上状态是最终状态，服务端状态只是同步状态和展示缓存。

## 8. Solidity 合约边界

### 8.1 合约目标

MVP 使用一个明确、易审查的 Escrow 合约，暂不拆成多个微型合约。

合约负责：

- 创建或初始化一个项目托管。
- 保存甲方和乙方地址。
- 保存里程碑金额和顺序。
- 接收模拟 ERC-20 代币。
- 校验只有正确角色可以执行操作。
- 在满足条件时释放当前里程碑金额。
- 记录关键事件。

### 8.2 合约不负责

- 存储合同全文。
- 存储图片和文件。
- 存储用户昵称和头像。
- 调用 AI。
- 发送移动通知。
- 读取 GitHub 内容。
- 处理复杂仲裁网络。
- 保管用户私钥。

### 8.3 建议合约组成

P0 只需要：

- `MilestoneEscrow.sol`
- `MockUSDC.sol`（仅测试网和本地测试使用）

P1 再考虑：

- `EscrowFactory.sol`：创建多个项目托管实例。
- `DisputeResolver.sol`：争议处理。
- `Splitter.sol`：多人分账。

### 8.4 合约关键约束

- 金额必须大于 0。
- 所有里程碑金额之和必须等于托管金额。
- 里程碑顺序不能被未授权角色修改。
- 已提交或已释放的里程碑不能被任意删除。
- 释放操作必须防止重复执行。
- 合约必须使用检查—生效—交互模式。
- ERC-20 转账使用安全封装。
- 关键操作必须发出事件。
- 任何资金转移都必须有明确的调用方和状态前置条件。
- 管理员权限必须最小化，不得设置可以绕过全部规则的隐藏后门。

### 8.5 关键事件

至少包含：

```text
ProjectCreated(projectId, client, contractor, token, totalAmount)
MilestoneCreated(projectId, milestoneId, amount, dueAt)
ProjectFunded(projectId, amount, transactionId)
MilestoneSubmitted(projectId, milestoneId, evidenceHash)
MilestoneApproved(projectId, milestoneId)
MilestoneReleased(projectId, milestoneId, recipient, amount)
ProjectCancelled(projectId)
```

事件字段要足够让 Node.js 索引器恢复主要项目状态。

### 8.6 合约安全最低要求

- 重入保护。
- 权限修饰器。
- 整数和金额边界检查。
- 不信任外部 token 合约返回值。
- 明确处理 token allowance 和 transferFrom 失败。
- 所有状态迁移有单元测试。
- 关键函数有异常路径测试。
- 不使用未解释的 `tx.origin`。
- 不使用中心化私钥代替用户签名。
- 部署地址、网络和 ABI 版本必须可追踪。

## 9. 链上、链下和文件存储边界

### 9.1 链上数据

只保存必须公开、可验证且与规则执行有关的数据：

- 钱包地址。
- 项目 ID 或不可变标识。
- 里程碑 ID、金额和状态。
- 截止时间。
- 资金托管和释放结果。
- 证据哈希或内容标识。
- 关键事件。

### 9.2 PostgreSQL 数据

保存产品体验和查询所需的数据：

- 用户展示资料。
- 钱包关联信息。
- 项目标题、描述和界面配置。
- 里程碑的长文本说明。
- 交付提交记录。
- 证据链接和文件元数据。
- 链上交易哈希、确认数和同步状态。
- 通知偏好。
- AI 生成结果。
- 索引器游标和错误记录。
- 审计日志。

PostgreSQL 不能覆盖链上最终结果。链上和数据库不一致时，必须通过事件同步纠正数据库。

### 9.3 对象存储或 IPFS

用于：

- 图片。
- 测试包说明。
- 合同附件。
- 交付文件。

应用数据库保存文件元数据和访问地址，链上保存必要的哈希或 CID。文件上传不能泄露私钥、助记词或敏感身份材料。

## 10. 技术架构

### 10.1 移动端

- Expo React Native。
- TypeScript strict 模式。
- Expo Router。
- 钱包连接 SDK，具体方案在实现阶段根据目标钱包和平台兼容性确定。
- 服务端数据请求层。
- 本地安全存储只保存会话和非敏感配置，不保存私钥。
- 统一的交易状态组件。
- 网络错误、交易错误和链上确认状态必须有独立展示。

### 10.2 Node.js 服务

Node.js 负责应用层能力：

- 钱包地址登录和会话。
- 项目和里程碑元数据。
- 权限检查。
- 证据元数据。
- 链上交易准备和查询。
- 链上事件索引。
- 通知和异步任务。
- AI 调用封装。
- 审计和错误记录。

后端不能代替用户签署资金交易，除非未来明确采用经过审计的智能账户方案。

### 10.3 API 风格

MVP 使用 Node.js REST API，不提前引入 GraphQL、微服务或复杂网关。

建议接口：

```text
GET    /v1/health
POST   /v1/auth/nonce
```

接口命名可以调整，但必须保持业务含义清楚。涉及链上交易的接口不得直接返回“已完成”，除非已经有可验证的交易哈希或事件状态。

### 10.4 PostgreSQL

生产方向使用 PostgreSQL，因为它适合：

- 关系型项目和用户数据。
- 交易索引。
- 权限查询。
- 审计记录。
- 事务和幂等操作。
- 后续搜索和报表。

本地开发可以使用 Docker PostgreSQL。若只是单独验证合约，也可以暂时不用数据库，但不能把这种 Demo 架构当成最终产品架构。

### 10.5 异步任务

初期可以使用一个 Worker 和 Redis 队列。后续部署到 AWS 时再根据负载选择 SQS、EventBridge 或其他服务。

异步任务包括：

- 链上事件重试和补偿同步。
- 交易状态轮询。
- 通知发送。
- AI 摘要。
- 超时检查。
- 文件处理。

### 10.6 Cloudflare 与 AWS

推荐的生产早期组合：

- Cloudflare：DNS、HTTPS、WAF、CDN；
- AWS ECS/Fargate：Node API 和 Worker；
- AWS RDS：PostgreSQL；
- AWS S3 或 Cloudflare R2：文件和图片；
- Redis 或 AWS SQS：异步任务；
- 第三方 RPC 服务：连接 EVM 网络。

以下内容不属于 MVP 必需项：

- Cloudflare Waiting Room；
- AWS AppSync；
- AWS Lambda@Edge；
- OpenSearch；
- 多区域容灾；
- Kubernetes；
- 自建区块链 RPC 节点。

## 13. 权限和安全

### 13.1 钱包安全

- 服务端不接收助记词和私钥。
- App 不打印私钥、签名原文和敏感 token。
- 钱包签名必须展示网络、合约、金额和操作类型。
- 所有交易必须由用户主动确认。
- 不允许通过后端接口直接替用户转账。

### 13.2 API 安全

- 每个资源都必须校验当前钱包或用户是否有权限访问。
- 禁止只依赖客户端传入的 `userId`。
- 所有输入进行 schema 校验。
- 写操作需要幂等键或防重复机制。
- 文件上传需要大小、类型和权限限制。
- 重要操作记录审计日志。

### 13.3 数据隐私

- 链上数据默认公开，界面必须提示用户。
- 个人资料和项目描述默认只对项目参与方可见。
- 公开链接需要不可枚举的随机标识。
- 支持删除链下数据，但明确说明无法删除已经上链的数据。

### 13.4 合约升级

MVP 优先使用简单、清楚、易审计的不可升级合约。若未来采用升级代理，必须单独设计管理员权限、时间锁、升级公告和回滚方案。

## 14. AI 使用边界

AI 不是资金和权限系统的一部分，只提供辅助能力。

### 14.1 P1 可做的 AI 能力

- 根据项目描述生成里程碑草案。
- 帮助检查验收标准是否含糊。
- 对乙方提交的说明做摘要。
- 根据提交记录生成项目进展报告。
- 识别可能需要人工确认的风险描述。

### 14.2 AI 不得执行的操作

- 不得自动释放资金。
- 不得自动确认里程碑。
- 不得自动修改合同金额。
- 不得替用户签名交易。
- 不得对争议做最终裁决。

AI 返回必须标明“建议”或“草稿”，用户可以编辑、忽略和重新生成。

## 21. 当前结论

本项目当前确定为：

> **一个使用 React Native 作为移动端、Solidity 作为资金和里程碑规则层、Node.js 作为应用服务、PostgreSQL 作为链下业务数据库、Cloudflare 和 AWS 作为部署基础设施的链上项目托管与里程碑分账 App。**

当前只做测试网和模拟代币，不发行平台代币，不做交易、不做 DAO、不做复杂市场、不做多链和真实资金服务。

当前最重要的成功标准不是“用了多少云服务”，而是：

> 两个用户能够清楚地创建一个项目、完成一次托管、提交一个里程碑、确认交付，并看到可信的资金释放结果。

- 视觉气质：专业、克制、带有 Web3 的技术感和交易确认感。
- 默认主背景：明亮冷灰，保证长时间阅读和金额信息的可读性；深色石墨黑作为可选外观模式。
- 默认主行动色：青绿色，用于连接、确认、释放和已验证状态；主题色可以切换为海蓝、琥珀或紫罗兰。
- 链上信息色：蓝色，用于网络、钱包地址、合约和交易链接。
- 待处理色：琥珀色，用于需要审核、等待和即将到期。
- 错误色：红色，只用于失败、拒绝和不可恢复提示。
- 使用轻量的玻璃材质：半透明表面、内高光、细边界和柔和阴影；玻璃效果必须服务于层级，不得降低文字对比度。
- 参考 Apple 系统界面的留白、圆角和状态反馈，但不复制品牌标识或页面。
- 主容器可以使用 18px 左右圆角，重复信息行使用 12—15px 圆角，避免所有元素都变成胶囊。
- 避免营销式大图、强渐变背景和无业务意义的装饰。
- 金额、交易哈希、钱包地址和区块号需要清晰的数字层级和等宽展示。
- 导航、交易、审核、钱包和安全状态优先使用统一图标库的线性图标；图标必须配合文字或无障碍标签，不能只依赖图形猜测含义。
- 设置中心必须提供简体中文和 English 两个语言选项；后续新增语言需要走国际化资源，不允许在页面内散落硬编码文本。
- 设置中心必须提供浅色和深色外观模式，默认使用浅色模式。
- 设置中心必须提供 Mint、Ocean、Amber、Violet 四个主题色，主题色只改变品牌行动色，不改变状态语义：绿色仍表示成功，琥珀仍表示待处理，红色仍表示错误。

### 22.3 交互基线

- 每个资金操作都必须在界面上展示金额、网络、接收地址和当前状态。
- “等待签名”“等待确认”“已成功”“已失败”必须使用不同状态，不允许只显示一个加载动画。
- 主要页面只突出一个下一步动作，避免同时放置多个同等权重的按钮。
- 项目为空、钱包未连接、网络错误、交易失败和证据不存在时，必须有明确空状态和恢复动作。
- 设计稿中的状态、文案和按钮不能引入主线之外的积分、代币、社交或交易市场概念。

## 23. Web 客户端基线

### 23.1 目标和技术边界

- 服务于与移动端相同的甲乙方项目合作流程；不是新增运营后台或其他业务产品。
- 工程位于 `apps/web`，使用 React DOM、TypeScript、Vite、Tailwind；独立启动、热更新和构建，不依赖 Expo、React Native Web 或 Metro。
- 桌面使用左侧导航、内容工作区、多列项目卡片和审核详情分栏。窄屏使用顶部菜单打开抽屉导航；不沿用移动 App 的底部导航。
- Web 延续移动端的冷灰背景、清晰金额层级、柔和圆角与细边界；半透明和模糊集中用于顶部导航与弹窗背景，内容卡片优先保证阅读清晰。
- 正文和主要说明使用 14–15px 层级，主要操作和项目状态不可缩成 9–10px 小字；中英文字体统一使用本地系统无衬线字体，不依赖远程字体加载。
- 项目列表桌面默认两列，窄屏单列；资金概览中的余额、释放金额和比例必须来自同一组业务数据，不添加虚构收益率、趋势或装饰性曲线。
- Web 默认采用紧凑工作台布局：桌面内容边距约 24–28px，普通卡片内边距约 20px；避免为了装饰性留白压缩有效编辑区。创建页宽屏提供编辑区与实时合作摘要，窄屏顺序排列。
- 合作摘要展示输入中的项目、合作方、阶段金额与顺序；金额核对区分未填写、无效、未分配完、超额和分配一致。金额一致不等于草稿完整，保存仍通过同一业务校验。
- 项目卡片的阶段条按实际状态显示待开放、可提交、待审核、已释放，并允许进入对应交付详情。侧栏合作概况使用项目与提交的实际数量；不使用虚构活动填满页面。
- 业务范围保持项目、里程碑、待处理、交易和偏好设置，不引入市场、社交、多链、复杂报表或运营管理。
- 中文 / English、浅色 / 深色 / 跟随系统、Mint / Ocean / Amber / Violet 均提供明确选择并持久化。用户输入的项目与证据原文不随界面语言改写。

### 23.2 当前实现阶段

当前 Web 与现有移动端一样处于本地演示阶段，支持：创建和编辑未托管草稿、1–5 个顺序里程碑、模拟托管、乙方提交说明与证据链接、甲方审核模拟释放、交易等待 / 成功 / 失败与重试。所有页面明确显示演示标记。

数据保存在浏览器 localStorage，不与移动端或其他浏览器同步；模拟角色切换不是正式身份验证。Web 通过独立的 EscrowGateway 接口隔离模拟逻辑，后续再接 Node API、钱包签名和真实链上事件。不得将本地模拟通过描述为真实 P0 链上闭环已完成。

金额输入和存储使用十进制字符串，运算使用 USDC 六位精度 bigint。总额、已释放、托管余额和进度统一由里程碑状态推导。当前演示固定 Ethereum Sepolia，不新增多链能力。
